# Razorpay Field Report

Generated by `scripts/harvest_errors.py` from 20 real captured payment objects and documentation read on 2026-08-25.

## Step 1 — documentation read before writing any test data

Fetched 2026-08-25 (fully rendered pages, not the static HTML — the docs site
renders these tables client-side and a plain HTTP fetch misses them):

- https://razorpay.com/docs/payments/payments/test-card-details/ — Test Cards for Indian Payments + Error Scenarios tables
- https://razorpay.com/docs/payments/payments/test-upi-details/ — UPI Collect / UPI Intent error-scenario tables
- https://razorpay.com/docs/errors/ — the generic API error-response shape
- https://razorpay.com/docs/errors/common/ — endpoint-independent common errors
- https://razorpay.com/docs/api/payments/entity/ — the Payment entity's own field list
- https://razorpay.com/docs/api/payments/payment-links/create-standard/ — Payment Links create request/response/errors

**Finding worth flagging:** the generic API error-response object documented at
https://razorpay.com/docs/errors/ uses unprefixed field names — `code`, `description`, `field`, `source`, 
`step`, `reason` — returned when an API *call itself* fails (bad request body, etc.). That is a
different, easily-confused schema from the Payment *entity's* own fields, which are prefixed —
`error_code`, `error_description`, `error_source`, `error_step`, `error_reason` — and describe why
a *payment* (not the API call that fetched it) failed. This project only ever reads the second
one (via fetch_payment / the payment.failed webhook), confirmed present on the live Payment entity
docs page as of 2026-08-25.

## Steps 2 & 3 — forcing failures: what actually happened

**UPI was not available as a payment method on this test account.** Every UPI-planned scenario's checkout page offered Card, Netbanking, and Wallet only — confirmed by direct observation, not inferred from a missing field. This is the honest, documented-gap outcome the harvest plan allows for: rather than invent a UPI payment, every UPI-planned link that got completed was completed via whichever real method was actually offered, and the `instrument`/`forced_by` fields below record what really happened, not what was planned (see `planned_instrument`/`planned_forced_by` on each record for the original intent).

- Real instruments captured: card, netbanking
- Distinct `error_reason` values across all 20 records: payment_cancelled, payment_failed

**Finding that shrinks the harvest's own premise:** all 19 card payments were forced using one of the 8 distinct documented "Error Scenario" card numbers from Razorpay's test-card docs (each reused across multiple checkouts — see the `forced_by` field on each record for exactly which number produced which payment), completed by clicking Failure on the mock bank screen as instructed. Every one of them came back with the same generic `error_reason: "payment_failed"` rather than the specific documented reason its card number is supposed to trigger (e.g. `insufficient_fund`, `card_declined`, `authentication_failed`, ...). On this account, at least, the per-card-number error mapping documented on the test-card page does not reproduce — the mock bank's Failure button appears to always return the same generic gateway authorization failure regardless of which of the 8 cards initiated it. This was not the expected result going in.

## Step 5 — reference_id duplicate-rejection probe

**Attempted with real credentials, not yet completed.** Every attempt this session hit `HTTP 429 {"error": {"code": "BAD_REQUEST_ERROR", "description": "Too many requests"}}` on the probe's first `create_payment_link` call — the same undocumented rate limit that slowed the main harvest (see BUILD_LOG.md for the full account). Cancelling an already-used link did not free capacity, which argues against this being the documented "30 Payment Links per business" cap specifically and for it being a time-windowed limit instead — but that is inference, not a confirmed mechanism. Razorpay's own Payment Links "Create" error list documents `payment link creation with reference ID already attempted` as a 400 response to a duplicate `reference_id`, which is the expected answer once this probe can actually run — but that is the documented answer, not yet the empirically confirmed one, and this project does not treat those as interchangeable. Re-run `make harvest` later to complete it; the result will be persisted to evidence/harvest_probe_result.json the first time it succeeds.

**Update, Phase 8, 27 Aug 2026 — the 429 mechanism is now confirmed, and it was not what Step 5 guessed.** Bypassing the retry/backoff logic entirely and firing a single raw `POST /v1/payment_links` at this account returned:

```json
{"error": {"code": "RATE_LIMIT_EXCEEDED", "description": "test mode limit of 30 reached for payment_link", "metadata": [], "reason": null, "source": null, "step": null}}
```

This *is* the documented "30 Payment Links per business" test-mode cap after all — the Step 5 inference above (favoring a time-windowed limit instead, based on cancelling not freeing capacity) was wrong. Cancelling a link removes it from the *payable* set but apparently does not free a slot against the creation cap; the cap counts links ever created, not links currently open. This account's cap was already exhausted by the Phase 1 harvest work (forcing checkout failures via the mock bank necessarily creates Payment Links/orders along the way), so no new real Payment Link can be created on it until Razorpay resets the cap — no documented reset window was found; flagged in `LIMITATIONS.md`. The reference_id duplicate-rejection probe (400 on a repeated `reference_id`) remains unconfirmed empirically for the same reason: it requires a successful creation to duplicate against, and this account cannot create one right now. `src/execute/executor.py` implements the documented 400 behavior defensively (treats it identically to local dedup, per Razorpay's own Payment Links error-list documentation) but that code path is untested against the live API — see `BUILD_LOG.md`'s Phase 8 entry for the full account of chasing this down.
