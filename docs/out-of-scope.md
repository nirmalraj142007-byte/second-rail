# Out of scope, and why

Every exclusion below has its reason attached. A bare list of things I did
not build reads as a list of things I ran out of time for. Several of these
I would not have built with unlimited time, because building them honestly
requires a registration, a licence, or a rulebook I do not have — and
building them dishonestly is worse than not building them.

Three groups: things I am **not permitted** to do, things I **chose not to**
do, and things I **cut** under a 33-hour budget. The distinction matters,
and conflating them is how a submission ends up claiming a capability it
does not have.

---

## Not permitted — regulatory, not preferential

### Mandates, subscriptions, e-NACH, UPI Autopay

**Reason: NPCI mandate retry rules are load-bearing and I do not have them
right.** Recurring-debit retry behaviour is governed by NPCI circulars that
specify permitted retry counts, timing, and pre-debit notification
requirements. Inventing a retry cadence for a mandate is not a modelling
simplification — it is the part a payments engineer would check first, and
getting it wrong invalidates every number downstream of it. A failed
recurring debit and a failed one-time payment look similar in a webhook and
are not similar at all in what you are allowed to do next. Second Rail
therefore never touches an episode originating from a mandate.

### Real SMS or WhatsApp sending

**Reason: TRAI's TCCCP regulations require DLT registration — registered
headers and pre-approved templates — for commercial messaging in India.** I
have no registered sender header and no approved templates, so I cannot send
a commercial message lawfully, and I am not going to describe test-mode
plumbing as a messaging system. What Second Rail actually does is set
Razorpay Payment Link's own `notify.sms` / `notify.email` flags in test mode
and claim nothing beyond that. Anywhere this project prices a
false-positive contact, the SMS cost is a *stated assumption* from
`outcome_model.md`, labelled as one, not a bill I paid.

### Storing, displaying, or logging a card PAN

**Reason: RBI card-tokenisation norms.** Merchants and their service
providers may not store card numbers; tokens are the only permitted
persistence. Second Rail never sees a PAN — the `payment` object Razorpay
returns does not include one, and nothing in `src/` reads, writes, renders,
or logs a card number. The synthetic generator does not produce one either,
so there is no path by which a PAN could enter the database even in test.

### Any real PII

**Reason: the Digital Personal Data Protection Act, 2023.** Processing real
personal data requires a lawful basis, notice, and purpose limitation that a
hackathon submission cannot satisfy. Every customer, payment, contact detail
and episode in this repo is synthetic, generated by the committed seeded
generator at `data/generator.py`. That file is committed specifically so this
claim is checkable rather than asserted.

## Chose not to — it belongs to someone else, or it would corrupt the evidence

### Multi-gateway routing

**Reason: that is Optimizer, and it is Razorpay's product.** Routing a
failed transaction to an alternate provider is exactly what Optimizer's
second-priority rules already do, in-session. Rebuilding it badly beside it
would invite the only genuinely dangerous question about this project — *is
this a feature we already ship?* — and deserve it. Second Rail sits
downstream of the point where Optimizer and Intelligent Payment Retry both
stop, which is when the session ends.

### Fraud and risk scoring

**Reason: it is a different problem with a different failure cost, and I
would be grading my own homework.** A risk score evaluated against labels I
generated myself proves nothing. Worse, the cost asymmetry is inverted from
this project's: a false negative in recovery costs one un-recovered payment;
a false negative in fraud costs a chargeback and a merchant relationship.
Episodes whose failure cause is a risk block are classified and then
deliberately routed to `no_action` — diagnosed, never acted on.

### Training any model

**Reason: nothing here has enough real labelled data to train on, and a
model trained on my own generator would be a closed loop wearing a lab
coat.** The 20 harvested error strings are real; 20 is a validation set, not
a training set. The classifier is a regex baseline plus a prompted LLM for
the unmatched tail, and the report states plainly where that arrangement
loses.

### Real-time streaming infrastructure

**Reason: batch replay is the honest shape of the evidence.** The claim
this project makes is about a 200-episode sealed batch with a stated
attribution window. Adding streaming would not change any reported number
and would add a subsystem I could not test under load. What streaming *would*
require is documented in [scaling-failures.md](scaling-failures.md) §1 rather
than hand-waved.

### An A/B testing framework

**Reason: there is no live traffic to split.** Both arms would be draws from
the same simulator, so the comparison would measure my own outcome model
against itself. The baseline comparison in the report (`FIXED_RETRY_AT_T30`)
is stated for what it is — a deterministic counterfactual over the same
sealed episodes, not an experiment.

## Cut under the budget — the skin, not the organ

These I would build with more hours. Each was cut against a named principle:
cut the presentation, never the guarantee.

### The web approval UI

**Cut on day one of the plan, not day nine.** The approval *gate* is the
thing that matters — a human keystroke above the auto-approve ceiling, with
the decision written to the audit log. Its skin is not. It fell back to a
JSON queue plus `make approve`. A read-only companion dashboard exists at
`src/webui/` for the demo, bound to 127.0.0.1 on a separate port from the
webhook receiver on purpose; it is a second window onto a run, not a
dependency of one. Nothing in the pipeline requires it to be running.

### Hinglish copy generation

**Reason: zero rubric weight and a real risk of sounding worse than
English.** Tone-matched Hinglish recovery copy was in the original plan.
English-only templates with LLM-filled slots do the same job, and the copy is
not where this project's argument lives.

### The breadth of the sensitivity sweep

**Cut from "every parameter" to exactly three:** response probability,
attribution window, and the goodwill proxy. Those are the three that actually
move the recovery figure, and each one is a named assumption in
`outcome_model.md` rather than a measurement. Sweeping twelve parameters
would have produced a wider band around the same invented quantity — more
work, no more evidence.

### The second baseline

**Kept one:** `FIXED_RETRY_AT_T30`, alongside the do-nothing case that the
uncontacted episodes already provide. A second baseline would have been a
third arm of the same simulator.

## Infrastructure deliberately absent

No queue, no auth provider, no messaging provider, no cloud deploy, no
Docker, no CI/CD, no multi-tenancy, no RBAC, no mobile UI.

**Reason: a judge has to be able to clone this and run it in under five
minutes with no API key.** Every one of those additions is a thing that can
be broken on someone else's machine, and the acceptance test that matters
most for this submission is `git clone && make setup && make eval`. The
absence is the feature. Where an absence has a real cost at volume, it is
named in [scaling-failures.md](scaling-failures.md) with the symptom and the
fix, rather than left as an implied "we'd just add Kubernetes".
